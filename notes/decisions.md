# The Relay: Decisions Log

A running log of every key architectural, technical, and measurement decision made during the development of The Relay. Every entry records the decision, alternatives considered, the reason or measurement behind it, and what it cost.

---

### D01: Pinned Research Paper Versions and SHA-256 Hashes
- **Decision:** Strictly enforce the exact pinned versions specified in the brief:
  1. *Attention Is All You Need* -> `arXiv:1706.03762v7`
  2. *Moshi: a speech-text foundation model for real-time dialogue* -> `arXiv:2410.00037v1`
  3. *Dynamic Chunking for End-to-End Hierarchical Sequence Modeling* -> `arXiv:2507.07955v2`
  Remove any unpinned version (such as `2410.00037v2.pdf`) from indexing. Enforce via SHA-256 verification in `scripts/verify_papers.py`.
- **Alternative:** Index whatever PDF was downloaded or use v2 of Moshi.
- **Reason:** The brief mandates citations to exact versions. Page numbers, section headings, and content differ between v1 and v2.
- **Cost:** An extra verification step at ingest time.

---

### D02: Gateway as Single Choke-Point
- **Decision:** All model calls from all pipeline steps pass through a centralized LLM gateway (`src/gateway.py`). Pipeline steps are forbidden from calling backends directly or retrying on their own.
- **Alternative:** Per-step retry loops in S1, S4, and S5.
- **Reason:** Per-step retries multiply under overload (retry storms), making system recovery mathematically impossible. A single gateway tracks shared RPM/TPM token buckets and coordinates backoff.
- **Cost:** The gateway is a single logical bottleneck and must handle concurrency, deadlines, and priorities correctly.

---

### D03: Buffered Draft Streaming vs. Gated Streaming
- **Decision:** S4 drafts are streamed into an internal memory buffer and only released to the user after S5 verification passes.
- **Alternative:** Direct token streaming to the user, or sentence-by-sentence gated streaming.
- **Reason:** Principle 1: *Correctness before speed*. Showing an unverified answer that later fails verification damages trust.
- **Cost:** Higher perceived time-to-first-token (`first_token_ms`), as TTFT includes the full drafting and verification duration.

---

### D04: Deterministic Citation Checker (Always Active)
- **Decision:** Verification in S5 relies on a zero-token deterministic Python checker (`src/citecheck.py`) that validates chunk ID existence, quoted span exact matching, and factual sentence citation coverage.
- **Alternative:** LLM-only verification (asking the model to judge citations).
- **Reason:** Deterministic checking costs zero provider tokens, cannot be rate-limited, runs in sub-millisecond time, and guarantees factual grounding.
- **Cost:** Cannot judge deep semantic subtlety without an optional second-stage LLM check.

---

### D05: Client Patience Limit (20.0s) & Request Deadlines
- **Decision:** Every request receives a deadline at arrival: `deadline = start_time + 20.0s`. Any queued or in-flight step whose deadline expires is cancelled immediately and marked given up.
- **Alternative:** Unbounded queues that process requests even after the human has left.
- **Reason:** Prevents zombie load. Under overload, completing work for an abandoned client wastes scarce token quota.
- **Cost:** Requests arriving during peak queue saturation are dropped or shed.

---

### D06: Status Mapping for Given-Up Requests in `results.csv`
- **Decision:** In `results.csv`, map client-abandoned / given-up requests to `status = timeout` (satisfying the brief's fixed enum: `ok`, `rate_limited`, `timeout`, `error`), while recording `outcome: given_up` in `traces.jsonl`.
- **Alternative:** Invent a custom `status = given_up` string in `results.csv`.
- **Reason:** Strict compliance with the assignment brief's CSV schema while preserving granular observability in traces.
- **Cost:** `make_tables.py` must cross-reference traces to distinguish network timeouts from client patience abandonment.

---

### D07: Stand-In Row Grading Policy
- **Decision:** Synthetic load-run rows in `results.csv` generated by the stand-in have `answer_grade = ""` (empty string). Only the curated 15+ question evaluation set in Phase 7 receives manual/rubric grades.
- **Alternative:** Auto-grade synthetic gibberish or fabricate grades.
- **Reason:** AGENTS.md rule: *Never fabricate grades or table numbers*. Synthetic load tests evaluate transport, rate-limiting, and queue dynamics, not semantic quality.
- **Cost:** Analysis script must filter for non-empty `answer_grade` when computing Table 3.

---

### D08: Open-Loop Load Generation
- **Decision:** Build an open-loop load generator where arrivals occur according to a fixed schedule regardless of server response times.
- **Alternative:** Closed-loop generator (e.g., waiting for request N to finish before sending N+1).
- **Reason:** Closed-loop generators artificially throttle themselves when the server slows down, hiding real overload.
- **Cost:** The generator must track scheduled vs. actual send time to ensure the test harness itself does not fall behind.

---

### D09: Priority Queue: In-Progress Over New Arrivals
- **Decision:** Gateway priority queue assigns Priority 1 to calls for requests already in progress (S4 drafting, S5 verification) and Priority 2 to new requests (S1 understand).
- **Alternative:** First-In First-Out (FIFO) queue.
- **Reason:** Protects tokens already spent. Finishing a 70% completed request wastes fewer provider tokens than starting new requests that may later be abandoned.
- **Cost:** New arrivals experience higher queue wait times during bursts.

---

### D10: Retrieval Architecture Across Settings A, B, and C
- **Decision:**
  - Setting A: Small chunks (~200 tokens), $k=8$, pure BM25.
  - Setting B: Medium chunks (~500 tokens), $k=4$, pure BM25.
  - Setting C: Medium chunks (~500 tokens), fetch $k=10$, local CPU dense re-ranking with `all-MiniLM-L6-v2` down to 4 chunks.
- **Alternative:** Call an external embedding API.
- **Reason:** External embeddings consume third-party quota. Local BM25 and CPU sentence-transformers cost zero provider tokens and remain fully reproducible.
- **Cost:** Setting C adds local CPU latency during retrieval.

---

### D11: Least Certain Assumptions
1. **Groq Rate Limits & Reset Behavior:** We assume the documented free tier limits reflect actual runtime limits and that headers (`x-ratelimit-remaining-*`) are consistently returned. (To be measured in Phase 3).
2. **Patience Threshold (20.0s):** We assume real engineers waiting for an urgent cited answer give up around 20 seconds. If real user patience is shorter (e.g. 10s), deadline dropping must trigger earlier.
3. **Stand-in Latency Fidelity:** We assume a log-normal distribution fitted to Groq probe latencies reasonably approximates real tail latency.
